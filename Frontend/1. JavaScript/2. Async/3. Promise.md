## 1. Promises: The Asynchronous State Machine

A **Promise** is an object representing the eventual completion (or failure) of an asynchronous operation. Before promises, JavaScript relied on callbacks. When nesting multiple asynchronous operations, callbacks led to deeply indented, unreadable code known as "Callback Hell."

A promise acts as a state machine that starts in one state and can transition to exactly one final state **once**.

### The 3 Promise States

* **`Pending`:** The initial state. The asynchronous operation is still working in the Web API background.
* **`Fulfilled` (Resolved):** The operation completed successfully. `.then()` is triggered.
* **`Rejected`:** The operation failed with an error. `.catch()` is triggered.

### Code Mechanics: Creating vs. Consuming

```javascript
// 1. Producing a Promise
const fetchUserData = new Promise((resolve, reject) => {
    const success = true;
    if (success) {
        resolve({ id: 1, name: "Sarah" }); // Moves state to 'Fulfilled'
    } else {
        reject(new Error("Network crashed")); // Moves state to 'Rejected'
    }
});

// 2. Consuming a Promise
fetchUserData
    .then((data) => console.log("Success:", data))
    .catch((error) => console.error("Failed:", error.message))
    .finally(() => console.log("Operation ended")); // Always runs

```

## 2. Async / Await: Syntactic Sugar over Promises

Introduced in ES2017, `async/await` is not a new asynchronous system. It is **syntactic sugar** built on top of native Promises and Generators. It allows you to write asynchronous code that reads like synchronous code, eliminating the visual clutter of `.then()` chaining.

### The Underlying Engine Mechanics

* **The `async` Keyword:** Placing `async` in front of a function forces it to **always return a Promise**. If you return a plain string or number from it, JavaScript automatically wraps that value inside a resolved promise (`Promise.resolve(value)`).
* **The `await` Keyword:** Can only be used inside an `async` function. When the engine encounters `await`, it **pauses function execution** at that exact line, steps out of the function to keep the main Call Stack free, and waits for the promise to settle.

```javascript
// Equivalent Code Comparison

// Traditional Chaining
function getVersionOld() {
    return fetch('/api/version')
        .then(res => res.json())
        .then(data => data.v);
}

// Modern Async/Await
async function getVersionNew() {
    try {
        const res = await fetch('/api/version'); // Pauses context here until resolved
        const data = await res.json();
        return data.v; 
    } catch (err) {
        console.error("Caught error:", err); // Replaces .catch()
    }
}

```

## 3. Combinators: `Promise.all` vs. `Promise.race`

When managing multiple asynchronous tasks concurrently, JavaScript provides built-in combinator methods.

### A. `Promise.all` (All-or-Nothing Parallelism)

* **Behavior:** Takes an array of promises and runs them concurrently in the background Web API threads.
* **Resolution:** It waits for **all** promises to fulfill and returns an array of results in the *exact same order* they were passed in.
* **🚨 The Catch (Short-Circuit Rejection):** If even **one** single promise rejects, the entire operation crashes immediately. It abandons all remaining pending promises and skips straight to the `.catch()` block.

```javascript
const p1 = Promise.resolve("User Data");
const p2 = new Promise((res) => setTimeout(() => res("Posts"), 100));
const p3 = Promise.resolve("Comments");

Promise.all([p1, p2, p3])
    .then(results => console.log(results)) // ["User Data", "Posts", "Comments"]
    .catch(err => console.log("One failed, everything aborted"));

```

### B. `Promise.race` (First to Finish Wins)

* **Behavior:** Takes an array of promises and runs them concurrently.
* **Resolution:** It returns the value or error of the **very first promise that settles** (either fulfills *or* rejects).
* **Best Used For:** Setting up network timeouts. If your API request takes longer than a local timer promise, the timeout promise wins and rejects the operation.

```javascript
const downloadImage = fetch('/heavy-image.png');
const timeout = new Promise((_, reject) => setTimeout(() => reject("Timeout!"), 500));

// Whichever runs faster wins the race
Promise.race([downloadImage, timeout])
    .then(img => console.log("Image loaded successfully"))
    .catch(err => console.error("Error or Timeout triggered:", err));

```

## 🚀 The Ultimate Interview Puzzle

Predict the console logs and time elapsed for this script:

```javascript
const delay = (ms) => new Promise(res => setTimeout(res, ms));

async function executeTasks() {
    console.log("Start");

    const task1 = delay(1000).then(() => "A");
    const task2 = delay(2000).then(() => "B");

    // Line X
    const result1 = await task1;
    console.log(`Finished ${result1}`);

    // Line Y
    const result2 = await task2;
    console.log(`Finished ${result2}`);
    
    console.log("End");
}

executeTasks();

```

### 🕵️‍♂️ Step-by-Step Execution Analysis

1. `"Start"` prints immediately.
2. `task1` and `task2` are initialized right after each other. **Crucial Detail:** The timers start counting down in the background Web API threads *at the exact same time*. They are running concurrently.
3. At `Line X`, the engine hits `await task1`. The `executeTasks` function halts for **1000ms**. Once it resolves, `"Finished A"` prints.
4. The engine moves to `Line Y` and hits `await task2`. Because `task2` was already counting down in the background while we waited for `task1`, it has already completed 1000ms of its 2000ms countdown.
5. The engine only needs to wait **1000ms more** for `task2` to finish. Then `"Finished B"` and `"End"` print.

### 🏆 Output & Total Time

The total time taken is **2 seconds** (not 3 seconds), because the promises were kicked off concurrently before being awaited sequentially.

```text
Start
Finished A   (at 1 second mark)
Finished B   (at 2 second mark)
End

```
