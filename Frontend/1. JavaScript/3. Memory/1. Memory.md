## 1. Garbage Collection (GC) in JavaScript

JavaScript manages memory automatically using an implicit system called **Garbage Collection**. When you create objects, strings, or variables, the engine allocates space on the **Heap** memory. When those values are no longer needed, the Garbage Collector frees that memory so the system doesn't run out of resources.

The modern engine relies on an algorithm called **Mark-and-Sweep**.

### The Mark-and-Sweep Algorithm

The engine establishes a set of **Roots** (the global `window` object in browsers, or `global` in Node.js).

1. **Mark Phase:** The Garbage Collector starts at the roots and traverses all references linked to them. Any object reachable from the roots is "marked" as alive.
2. **Sweep Phase:** The engine scans the Heap memory. Any object that was *not* marked during the traversal is deemed unreachable and is completely deleted from memory.

```javascript
let user = { name: "Alex" }; // Object allocated in Heap. 'user' points to it.
user = null; // The reference is severed. The object is now unreachable and will be swept.

```

## 2. Memory Leaks: The Reachability Trap

A **Memory Leak** occurs when objects are no longer needed by the application's business logic, but due to forgotten references, they remain reachable from the Global Roots. Because they are reachable, the Mark-and-Sweep algorithm cannot destroy them.

### Common Memory Leak Scenarios

#### Scenario A: Forgotten Timers or Listeners

```javascript
const heavyData = new Array(1000000).fill("💾");

setInterval(() => {
    // This closure captures 'heavyData'
    console.log("Running task...");
}, 1000); 

// If you forget to clearInterval, heavyData stays in the heap forever 
// because the background Web API timer keeps a live link to this closure!

```

#### Scenario B: Detached DOM Nodes

This happens when you delete an HTML element from the webpage, but a JavaScript variable still holds a reference to it.

```javascript
let detachedButton = document.getElementById("submit-btn");
document.body.removeChild(detachedButton); 

// The button is gone from the screen, but it CANNOT be garbage collected 
// because 'detachedButton' still points to it in memory.

```

## 3. WeakMap & WeakSet: The Garbage-Collection Loophole

Standard JavaScript `Map` and `Set` structures hold **Strong References** to their keys and values. If an object is placed inside a standard `Map`, that object will **never** be garbage collected, even if all other variables pointing to it are deleted.

```javascript
let passenger = { name: "John" };
const manifest = new Map();

manifest.set(passenger, "Seat 12A");
passenger = null; // Severing the primary reference

// Even though passenger = null, the object STILL exists in memory 
// because 'manifest' holds a strong reference to it!
console.log(manifest.size); // 1

```

### The Weak Solution

`WeakMap` and `WeakSet` store **Weak References** to objects. A weak reference does *not* prevent garbage collection. If the *only* references remaining to an object are inside a `WeakMap` or `WeakSet`, the Garbage Collector will instantly destroy that object and clear it out.

### Strict Rules of Weak Structures:

1. **Keys Must Be Objects/Symbols:** You cannot use primitives (like numbers or strings) as keys because primitives cannot be garbage collected.
2. **Not Iterable:** You cannot run `forEach`, `.keys()`, or `.size` on a `WeakMap/WeakSet`. Because garbage collection happens unpredictably in the background, you can never reliably predict exactly how many items are currently inside it.

## 🛠️ Real-World Code Comparison: Caching Metadata

Imagine building an analytics library that tracks metadata for active DOM elements.

### ❌ The Memory Leak Way (Using a Standard Map)

```javascript
let button = document.querySelector("#action-btn");
const elementMetadata = new Map();

elementMetadata.set(button, { clicks: 10 });

// Later, the UI changes and the button is removed
button.remove();
button = null; 

// 🚨 BUG: The metadata map still strongly retains the button element and its metadata. 
// The entire DOM element sub-tree is leaked in the Heap!

```

### The Leak-Safe Way (Using a WeakMap)

```javascript
let button = document.querySelector("#action-btn");
const elementMetadata = new WeakMap();

elementMetadata.set(button, { clicks: 10 });

// Later, the UI changes and the button is removed
button.remove();
button = null; 

//  SUCCESS: The next time the Garbage Collector runs, it detects that 'button' has 
// no external strong references. It automatically deletes the button AND removes 
// its corresponding metadata entry from the WeakMap automatically.

```

## 📋 Quick Matrix for Reference

| Feature | Standard `Map` / `Set` | `WeakMap` / `WeakSet` |
| --- | --- | --- |
| **Reference Type** | Strong Reference | Weak Reference |
| **Allowed Data Types** | Any type (Primitives & Objects) | Keys must be Objects or Symbols |
| **Prevents Garbage Collection?** | **Yes** | ❌ **No** |
| **Iteration & Size Methods** | Supported (`.size`, `keys()`, `forEach`) | Unsupported (Completely non-iterable) |
| **Primary Use Case** | General data caching and storage. | Attaching metadata to DOM nodes or managing private class variables without causing memory leaks. |
