Let’s deep dive straight into the gears of **Hoisting**.

Most resources say, *"Hoisting moves variables and functions to the top of the code."* This is a conceptual lie. The JavaScript engine doesn't physically move your code.

Instead, hoisting is a byproduct of how the **Execution Context** is created. During the **Creation Phase**, the engine scans your code and sets up memory space for your declarations *before* it executes a single line of code.

Here are the exact mechanics of how different items are hoisted:

| Type | Hoisting Behavior | Initialization Value |
| --- | --- | --- |
| **Function Declaration** | Fully Hoisted | The actual function body |
| **`var` Variables** | Hoisted | `undefined` |
| **`let` and `const**` | Hoisted | **Uninitialized** (Locked in Temporal Dead Zone) |
| **Class Declarations** | Hoisted | **Uninitialized** |
| **Function Expressions** | Governed by the variable keyword (`var`, `let`, `const`) | `undefined` or Uninitialized |

---

### The Temporal Dead Zone (TDZ)

When a block is entered, all `let` and `const` variables inside it are allocated memory space (hoisted), but they are marked as **uninitialized**. The period between entering the scope and the actual line where the variable is declared is called the **Temporal Dead Zone**. Accessing them here throws a `ReferenceError`.

## 🕵️‍♂️ Step-by-Step Execution Breakdown

Let's dissect exactly what the JavaScript engine does during the Creation and Execution phases inside `test()`.

### Phase 1: Creation Phase (Inside `test`)

When `test()` is invoked, a new function Execution Context is created. The engine scans the function block for declarations:

1. **Function Declarations take priority.** It finds `function foo() {}` at the very bottom. It hoists `foo`, allocates memory, and points it to the function body.
2. **`var` variables are scanned.** It finds `var foo = 2` inside the `if` block. (Note: `var` ignores `if` blocks because it is function-scoped).
3. **Collision management:** The engine sees that the name `foo` is already taken by a fully hoisted function declaration. Because function declarations override `var` declarations during hoisting, the `var` is ignored, and `foo` remains pointed to the function.

At the starting line of execution inside `test()`, the local environment looks like this:

```javascript
// Hidden state inside test() local scope at line 1:
foo = function foo() {} 

```

### Phase 2: Execution Phase (Line-by-Line)

* **Line 4: `console.log(foo);**`
JavaScript looks for `foo` in the local scope. It finds it initialized as a function.
* **Output 1:** `[Function: foo]`


* **Line 6: `if (false) { var foo = 2; }**`
The condition is `false`, so the code inside the block does not run. `foo` is **never** reassigned to `2`.
* **Line 10: `console.log(foo);**`
`foo` is still exactly what it was—the hoisted function.
* **Output 2:** `[Function: foo]`


* **Line 12: `foo = 3;**`
The local variable `foo` is now reassigned to the primitive number `3`.
* **Line 13: `return;**`
The function terminates and exits. The local variable `foo` (which was `3`) is swept away with the environment.
* **Line 18: `console.log(foo);**`
We are now back in the global scope. The global variable `foo` on Line 1 was never touched by the function because the local `foo` completely shadowed it.
* **Output 3:** `1`

## 1. Why are `let` and `const` not initialized during hoisting?

The short answer is: **To prevent silent bugs and enforce predictable code.**

When JavaScript was designed in 1995, `var` was the only way to declare variables. Its hoisting behavior (initializing to `undefined`) allowed you to accidentally use variables before defining them without the program crashing. This led to massive, hard-to-trace bugs in large applications.

When the TC39 committee introduced `let` and `const` in ES6 (2015), they wanted to fix this. They decided that while the engine *must* know about the variable's existence beforehand (hoisting), it should **strictly forbid** anyone from accessing it until the code actually initializes it.

### The Under-the-Hood Mechanism

When the engine compiles a block, it puts `let` and `const` variables into a special state called the **Temporal Dead Zone (TDZ)**.

* **With `var`:** Memory is allocated, and the engine automatically writes the primitive value `undefined` into that memory slot during compilation.
* **With `let`/`const`:** Memory is allocated, but it is marked with a special internal flag: **`uninitialized`**.

If the interpreter encounters a variable read instruction and sees the `uninitialized` flag, it is hard-coded to immediately throw a `ReferenceError`.

---

## 2. Why do function declarations take priority over `var`, even if the `var` is at the top?

To understand this, you have to look at the strict phases of the JavaScript Engine's **Creation Phase** (Compilation).

When an execution context (like a function) is born, the engine runs a highly structured, multi-pass scan over the code. The order of operations inside the V8 engine is explicitly written into the ECMAScript specification:

1. **Pass 1 (Function Hoisting):** The engine scans the entire block *exclusively* for formal function declarations (`function name() {}`). It creates bindings for them in the environment record and fills them with the function's code body.
2. **Pass 2 (Variable Hoisting):** The engine resets and scans the code *again*, this time looking for `var`, `let`, and `const` declarations.

### What happens when they collide?

Let's look at your exact scenario:

```javascript
function test() {
    var foo = 2; // var is at the top
    function foo() {} // function is at the bottom
}

```

* **During Pass 1:** The engine sees `function foo() {}`. It creates a key in memory called `foo` and points it to the function block.
* **During Pass 2:** The engine encounters `var foo`. It checks its memory register: *"Does a property named `foo` already exist?"* **Yes, it does.** Because a function declaration is a heavier, more complex binding than a simple unassigned `var`, the ECMAScript spec dictates: **If a property name already exists in the environment record and it's a function declaration, skip the `var` initialization.** The engine literally says, *"I already have a fully fleshed-out function named `foo` here. I am not going to overwrite it with `undefined` just for an unassigned `var` declaration."*

Thus, the function space wins the race, regardless of whether it was written on line 2 or line 200.
