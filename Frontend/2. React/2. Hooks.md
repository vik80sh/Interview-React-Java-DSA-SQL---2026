## 1. `useMemo` & `useCallback` (The Memoization Twins)

Both hooks exist for exactly one purpose: **caching data across renders to prevent unnecessary computations and child re-renders.** They only recompute when an item in their dependency array changes.

The difference lies entirely in *what* they cache in memory.

### The Core Distinctions

* **`useMemo`:** Caches the **result of a function call** (a primitive, an object, an array). It executes the function during rendering and stores the return value.
* **`useCallback`:** Caches the **function definition itself**. It does *not* execute the function; it just hoards the function's memory address pointer so it doesn’t get recreated as a new object instance on every render.

```javascript
import { useMemo, useCallback, useState } from 'react';

function ProductPage({ productId, theme }) {
  const [count, setCount] = useState(0);

  // 1. useMemo: Prevents re-running an expensive loop unless productId changes
  const heavyData = useMemo(() => {
    return computeMassiveData(productId); 
  }, [productId]); // If 'count' updates, this does NOT re-run

  // 2. useCallback: Prevents creating a new function reference on every render
  const addToCart = useCallback(() => {
    console.log(`Adding ${productId} to cart`);
  }, [productId]); // Returns the identical function reference unless productId changes
}

```

#### 🚨 Crucial Interview Note: The `React.memo` Connection

Passing a standard inline function to a child component breaks child optimization:

```javascript
<ChildComponent onSubmit={() => doSomething()} />

```

Because functions are objects in JavaScript, every render creates a fresh memory address. Even if `ChildComponent` is wrapped in `React.memo`, it sees a "new" prop and forces a re-render. You **must** wrap the parent function in `useCallback` to make `React.memo` actually work.

## 2. `useReducer` (State Machine Management)

`useReducer` is the preferred alternative to `useState` when managing complex component state that involves multiple sub-values, or when the next state depends heavily on the previous state. It decouples the state architecture entirely from the UI components.

### The Architectural Blueprint

It relies on a unidirectional data flow pattern (similar to Redux):

1. **State:** The single source of truth object.
2. **Action:** A plain JavaScript object describing *what event* just happened (e.g., `{ type: 'INCREMENT' }`).
3. **Reducer:** A **pure function** that takes the `(currentState, action)` and computes the brand-new state object without mutating the old one.

```javascript
const initialState = { count: 0, status: "Idle" };

// Pure reducer function: Predictable, deterministic, testable
function counterReducer(state, action) {
  switch (action.type) {
    case 'FETCH_START':
      return { ...state, status: "Loading" };
    case 'INCREMENT':
      return { ...state, count: state.count + 1, status: "Success" };
    case 'DECREMENT':
      return { ...state, count: state.count - 1, status: "Success" };
    default:
      return state;
  }
}

// Inside your component:
const [state, dispatch] = useReducer(counterReducer, initialState);

// Triggering state updates:
dispatch({ type: 'INCREMENT' });

```

## 3. `useRef` (The Escape Hatch)

`useRef` returns a mutable object whose `.current` property persists across the entire lifecycle of the component.

### The Two Faces of `useRef`

#### Use Case A: Referencing DOM Nodes

Directly grabbing a physical HTML element from the browser DOM tree to trigger manual focus, text selection, animations, or measurement.

```javascript
const inputRef = useRef(null);

const handleFocus = () => {
  inputRef.current.focus(); // Accesses the real browser DOM element directly
};

return <input ref={inputRef} />;

```

#### Use Case B: Storing Instance Variables (The Hidden State)

Unlike `useState`, **updating a ref’s `.current` value does NOT trigger a component re-render.** It behaves exactly like an instance variable on a class component. It is perfect for storing values that need to be remembered across renders but have no direct visual layout representation on the screen (like timer IDs).

```javascript
const timerId = useRef(null);

const startTimer = () => {
  timerId.current = setInterval(() => {
    console.log("Tick");
  }, 1000); // Remembers the ID across renders without causing UI layout repaints
};

const stopTimer = () => {
  clearInterval(timerId.current); // Safely clears it whenever requested
};

```

## 4. The Context API (Global Portal)

The Context API provides a way to pass data down through the component tree without having to manually pass props through every single intermediate level—a problem known as **Prop Drilling**.

```text
Without Context: Parent ---> Child ---> Grandchild ---> Target (Prop Drilling)
With Context:    Context Portal -----------------------> Target (Direct Access)

```

### The Render Performance Trap

Context is fantastic for global state changes that happen rarely (like language switching or UI theme toggles). However, **it is not a state management tool like Redux.** * **The Trap:** Whenever a value stored inside a Context Provider changes, **every single component that consumes that context via `useContext` will immediately re-render**, completely bypassing `React.memo` or parent-child container safety walls.

* **The Solution:** To fix this in large applications, you must break large monolithic context states up into smaller, hyper-focused individual Context Providers (e.g., separate `UserContext` from `ThemeContext`).

```javascript
import { createContext, useContext, useState } from 'react';

// 1. Create the Portal
const ThemeContext = createContext(null);

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState("dark");
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

// 2. Consume the Portal (Anywhere deep in the sub-tree)
function DeepChildButton() {
  const { theme, setTheme } = useContext(ThemeContext);
  return <button className={theme}>Theme Button</button>;
}

```

## 📊 Summary Cheat Sheet

| Hook / API | Returns | Triggers Re-render on Value Change? | Primary Use Case |
| --- | --- | --- | --- |
| **`useMemo`** | A memoized *value* snapshot. | ❌ No (Calculates *during* render) | Caching heavy arrays, data sorting, or complex object computations. |
| **`useCallback`** | A memoized *function reference*. | ❌ No | Preventing broken function references passed to optimized child structures. |
| **`useReducer`** | `[state, dispatch]` | **Yes** (when state changes) | Managing highly complex states with multi-action workflows. |
| **`useRef`** | An object containing `{ current: value }`. | ❌ **No** | Storing persistent background values or accessing direct DOM nodes. |
| **`Context`** | A Component Provider / Hook Accessor. | **Yes** (For all components consuming it) | Passing global configuration values across highly nested layers. |
