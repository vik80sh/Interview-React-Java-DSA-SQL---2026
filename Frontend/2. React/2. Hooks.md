## 1. `useMemo` & `useCallback` (The Memoization Twins)

Both hooks exist for exactly one purpose: **caching data across renders to prevent unnecessary computations and child re-renders.** They only recompute when an item in their dependency array changes.

The difference lies entirely in *what* they cache in memory.

### The Core Distinctions

* **`useMemo`:** Caches the **result of a function call** (a primitive, an object, an array). It executes the function during rendering and stores the return value.
* **`useCallback`:** Caches the **function definition itself**. It does *not* execute the function; it just hoards the function's memory address pointer so it doesn’t get recreated as a new object instance on every render.

```javascript
import { useMemo, useCallback, useState } from 'react';

function ProductPage({ productId, theme }) {
  const [count, setCount] = useState(0);

  // 1. useMemo: Prevents re-running an expensive loop unless productId changes
  const heavyData = useMemo(() => {
    return computeMassiveData(productId); 
  }, [productId]); // If 'count' updates, this does NOT re-run

  // 2. useCallback: Prevents creating a new function reference on every render
  const addToCart = useCallback(() => {
    console.log(`Adding ${productId} to cart`);
  }, [productId]); // Returns the identical function reference unless productId changes
}

```

#### 🚨 Crucial Interview Note: The `React.memo` Connection

Passing a standard inline function to a child component breaks child optimization:

```javascript
<ChildComponent onSubmit={() => doSomething()} />

```

Because functions are objects in JavaScript, every render creates a fresh memory address. Even if `ChildComponent` is wrapped in `React.memo`, it sees a "new" prop and forces a re-render. You **must** wrap the parent function in `useCallback` to make `React.memo` actually work.

## 2. `useReducer` (State Machine Management)

`useReducer` is the preferred alternative to `useState` when managing complex component state that involves multiple sub-values, or when the next state depends heavily on the previous state. It decouples the state architecture entirely from the UI components.

### The Architectural Blueprint

It relies on a unidirectional data flow pattern (similar to Redux):

1. **State:** The single source of truth object.
2. **Action:** A plain JavaScript object describing *what event* just happened (e.g., `{ type: 'INCREMENT' }`).
3. **Reducer:** A **pure function** that takes the `(currentState, action)` and computes the brand-new state object without mutating the old one.

```javascript
const initialState = { count: 0, status: "Idle" };

// Pure reducer function: Predictable, deterministic, testable
function counterReducer(state, action) {
  switch (action.type) {
    case 'FETCH_START':
      return { ...state, status: "Loading" };
    case 'INCREMENT':
      return { ...state, count: state.count + 1, status: "Success" };
    case 'DECREMENT':
      return { ...state, count: state.count - 1, status: "Success" };
    default:
      return state;
  }
}

// Inside your component:
const [state, dispatch] = useReducer(counterReducer, initialState);

// Triggering state updates:
dispatch({ type: 'INCREMENT' });

```

## 3. `useRef` (The Escape Hatch)

`useRef` returns a mutable object whose `.current` property persists across the entire lifecycle of the component.

### The Two Faces of `useRef`

#### Use Case A: Referencing DOM Nodes

Directly grabbing a physical HTML element from the browser DOM tree to trigger manual focus, text selection, animations, or measurement.

```javascript
const inputRef = useRef(null);

const handleFocus = () => {
  inputRef.current.focus(); // Accesses the real browser DOM element directly
};

return <input ref={inputRef} />;

```

#### Use Case B: Storing Instance Variables (The Hidden State)

Unlike `useState`, **updating a ref’s `.current` value does NOT trigger a component re-render.** It behaves exactly like an instance variable on a class component. It is perfect for storing values that need to be remembered across renders but have no direct visual layout representation on the screen (like timer IDs).

```javascript
const timerId = useRef(null);

const startTimer = () => {
  timerId.current = setInterval(() => {
    console.log("Tick");
  }, 1000); // Remembers the ID across renders without causing UI layout repaints
};

const stopTimer = () => {
  clearInterval(timerId.current); // Safely clears it whenever requested
};

```

## 4. The Context API (Global Portal)

The Context API provides a way to pass data down through the component tree without having to manually pass props through every single intermediate level—a problem known as **Prop Drilling**.

```text
Without Context: Parent ---> Child ---> Grandchild ---> Target (Prop Drilling)
With Context:    Context Portal -----------------------> Target (Direct Access)

```

### The Render Performance Trap

Context is fantastic for global state changes that happen rarely (like language switching or UI theme toggles). However, **it is not a state management tool like Redux.** * **The Trap:** Whenever a value stored inside a Context Provider changes, **every single component that consumes that context via `useContext` will immediately re-render**, completely bypassing `React.memo` or parent-child container safety walls.

* **The Solution:** To fix this in large applications, you must break large monolithic context states up into smaller, hyper-focused individual Context Providers (e.g., separate `UserContext` from `ThemeContext`).

```javascript
import { createContext, useContext, useState } from 'react';

// 1. Create the Portal
const ThemeContext = createContext(null);

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState("dark");
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

// 2. Consume the Portal (Anywhere deep in the sub-tree)
function DeepChildButton() {
  const { theme, setTheme } = useContext(ThemeContext);
  return <button className={theme}>Theme Button</button>;
}

```

## 1. Deep Dive: Sending Parameters with `useReducer` (Action Payloads)

In production apps, an action rarely just tells the reducer *what* to do (`type`). It almost always needs to carry data along with it (e.g., *which* item to delete, *what* text the user typed, or *the data* fetched from an API).

To do this, we follow the standard Redux convention by adding a **`payload`** property to our action object. The `payload` can be a primitive, an array, or a massive object.

### The Code Implementation

```javascript
import { useReducer } from 'react';

// 1. Initial State
const initialCartState = {
  items: [], // Array of objects: { id, name, price, quantity }
  totalAmount: 0
};

// 2. Deep Dive Reducer Logic
function cartReducer(state, action) {
  switch (action.type) {
    case 'ADD_ITEM': {
      // 🚨 DEEP DIVE: The parameter is received inside action.payload
      const updatedTotalAmount = state.totalAmount + action.payload.price * action.payload.quantity;
      
      const existingItemIndex = state.items.findIndex(item => item.id === action.payload.id);
      let updatedItems = [...state.items];

      if (existingItemIndex > -1) {
        // Item already exists, update its quantity immutably
        const existingItem = state.items[existingItemIndex];
        updatedItems[existingItemIndex] = {
          ...existingItem,
          quantity: existingItem.quantity + action.payload.quantity
        };
      } else {
        // New item, push the payload directly into the items array
        updatedItems.push(action.payload);
      }

      return {
        items: updatedItems,
        totalAmount: updatedTotalAmount
      };
    }

    case 'REMOVE_ITEM': {
      // 🚨 DEEP DIVE: The parameter passed here is a simple ID primitive
      const targetItem = state.items.find(item => item.id === action.payload);
      if (!targetItem) return state;

      const updatedItems = state.items.filter(item => item.id !== action.payload);
      const updatedTotal = state.totalAmount - (targetItem.price * targetItem.quantity);

      return {
        items: updatedItems,
        totalAmount: updatedTotal
      };
    }

    default:
      return state;
  }
}

// 3. Component Usage
export function ShoppingCart() {
  const [state, dispatch] = useReducer(cartReducer, initialCartState);

  const handleAddMacbook = () => {
    // Kicking off the dispatch with a complex object parameter
    dispatch({ 
      type: 'ADD_ITEM', 
      payload: { id: 'p1', name: 'MacBook Pro', price: 2000, quantity: 1 } 
    });
  };

  const handleRemoveItem = (id) => {
    // Kicking off the dispatch with a primitive parameter
    dispatch({ type: 'REMOVE_ITEM', payload: id });
  };

  return (
    <div>
      <h3>Total: ${state.totalAmount}</h3>
      <button onClick={handleAddMacbook}>Add MacBook</button>
      {state.items.map(item => (
        <button key={item.id} onClick={() => handleRemoveItem(item.id)}>Remove {item.name}</button>
      ))}
    </div>
  );
}

```

## 2. Deep Dive: Passing Refs across Components via `forwardRef`

By default, React components are completely **encapsulated**. You cannot pass a `ref` down to a custom child component as a regular prop.

### ❌ The Core Breakdown: Why `props.ref` Fails

If you try to write this code, it will fail silently and throw a console warning:

```javascript
// This does NOT work
function CustomInput(props) {
  return <input ref={props.ref} />; 
}
// React treats 'ref' as a protected keyword, not a normal prop!

```

If a parent component needs to directly access a physical HTML input tag buried deep inside a child component (to trigger focus, trigger media playback, or read coordinate dimensions), you must use **`forwardRef`**.

`forwardRef` intercepts the protected `ref` attribute from the parent invocation and explicitly injects it as the **second argument** of the child function.

### The Code Implementation

```javascript
import { useRef, forwardRef } from 'react';

// 1. Child Component wrapped in forwardRef
// Notice it accepts two arguments: (props, ref)
const MyCustomInput = forwardRef((props, ref) => {
  return (
    <div className="input-wrapper">
      <label>{props.label}</label>
      {/* 🚨 THE HOOK: The parent's ref pointer is explicitly wired to this real input element */}
      <input ref={ref} type="text" className="styled-input" />
    </div>
  );
});

// Good practice for debugging in React DevTools
MyCustomInput.displayName = 'MyCustomInput';

// 2. Parent Component
export function ParentForm() {
  // Create a local reference hook
  const textInputRef = useRef(null);

  const focusInputOnDemand = () => {
    // 🚨 DEEP DIVE: textInputRef.current now directly controls the actual 
    // <input> tag sitting inside the child component memory frame!
    textInputRef.current.focus();
    textInputRef.current.style.borderColor = 'red'; 
  };

  return (
    <div className="form-container">
      {/* We pass the ref normally down to the wrapped child element */}
      <MyCustomInput label="Username:" ref={textInputRef} />
      
      <button onClick={focusInputOnDemand}>
        Force Focus Child Input
      </button>
    </div>
  );
}

```

## 🧠 Master Level Architectural Caveat: `useImperativeHandle`

When using `forwardRef`, you expose the **entire native DOM node** to the parent. The parent can then manipulate absolutely anything—change the value, delete CSS classes, or break styles.

If you want to protect your components and restrict *only* specific allowed methods to the parent, you pair `forwardRef` with **`useImperativeHandle`**.

```javascript
import { useRef, forwardRef, useImperativeHandle } from 'react';

const SecureInput = forwardRef((props, ref) => {
  const localInputRef = useRef(null);

  // Expose ONLY selective methods to the parent, keeping the rest private
  useImperativeHandle(ref, () => ({
    triggerSecureFocus() {
      console.log("Custom processing done before focusing...");
      localInputRef.current.focus();
    }
  }));

  return <input ref={localInputRef} type="password" />;
});

// Parent side call:
// parentRef.current.triggerSecureFocus() works!
// parentRef.current.style.borderColor = 'red' fails completely (safely encapsulated).

```
