## 1. The Virtual DOM (VDOM)

The **Virtual DOM** is a lightweight, structural blueprint of the real DOM kept completely in-memory. It is a tree made of plain JavaScript objects (`React.createElement` outputs).

Updating the real browser DOM is extremely expensive because it triggers heavy Layout and Paint calculations. The Virtual DOM solves this by allowing React to calculate UI modifications entirely in-memory first.

```javascript
// How a React Element looks under the hood in memory
{
  type: 'button',
  props: {
    className: 'primary-btn',
    children: 'Click Me'
  },
  key: null,
  ref: null
}

```

---

## 2. Rendering

In React, **Rendering** is the execution phase where the component functions run to compute what the UI *should* look like.

* **The Trigger:** A render is triggered by an initial page load or a subsequent change in **State** (`useState`) or **Props**.
* **The Process:** React starts at the root component and walks down the tree, executing your component functions. Each function returns JSX, which compiles down into a new Virtual DOM tree.
* **🚨 Critical Interview Distinction:** **Rendering is NOT painting.** Rendering is purely a JavaScript calculation step. A component can render dozens of times without touching a single real pixel on the screen.

---

## 3. Reconciliation & The Diffing Algorithm

Once React calculates a new Virtual DOM tree during a render cycle, it needs to compare it with the previous Virtual DOM tree to see exactly what changed. This strategy of comparing trees and syncing updates to the real DOM is called **Reconciliation**.

To perform this comparison rapidly, React uses a **Diffing Algorithm** governed by two primary heuristics:

### Rule 1: Element Type Changes

If two elements at the same position have different HTML/Component tags (e.g., swapping a `<div>` for a `<section>`, or a `<Header>` for a `<Footer>`), React destroys the entire old DOM sub-tree, unmounts all children, and builds a brand-new DOM structure from scratch.

### Rule 2: The Key Attribute

When dealing with dynamic arrays, React needs a way to track identity across renders. If you do not provide a unique, stable `key`, React defaults to using the array indexes (`0, 1, 2...`).

* If you insert an item at the beginning of the list, index `0` changes, index `1` changes, and so on. React assumes *every* item changed and forces a complete re-render of the entire list.
* With a stable `key` (like a database ID), React moves the physical DOM node to its new position without re-rendering its contents.

## 4. React Fiber Architecture

Before React 16, the reconciliation engine used a **Stack Reconciler**. It traveled down the component tree using recursive function calls. Because the Call Stack cannot be paused, a massive tree update would lock up the main thread for 100ms+, causing visible UI stuttering and drops in frame rates.

**React Fiber** is the total rewrite of React’s core reconciliation engine. It changes reconciliation from synchronous recursive rendering to an **asynchronous, interruptible work-loop**.

### How Fiber Works

Fiber breaks down the massive, monolithic tree update into tiny, bite-sized fragments of computation called a **Fiber Node**. A Fiber node is simply a working unit of JavaScript memory that contains pointers to its child, sibling, and parent elements.

```text
       [ Root Fiber ]
             | (child)
       [ App Fiber ]
        /         \ (sibling)
 [ Sidebar ] ----> [ Main Content ]

```

### The Two Phases of Fiber

Fiber splits the update pipeline into two separate operational phases:

#### Phase 1: The Render/Reconciliation Phase (Asynchronous)

* React builds a speculative "work-in-progress" Fiber tree in the background.
* **Interruptible:** If the user starts typing into an input field midway through this phase, React will pause its background rendering task, prioritize handling the user's keystroke, and then discard or resume the background rendering work.
* This phase is pure calculation—it runs hooks, executes component functions, and is completely safe to pause or restart.

#### Phase 2: The Commit Phase (Synchronous)

* React takes the finished work-in-progress tree and applies the minimal calculated changes to the real DOM using native browser APIs (`appendChild`, `removeChild`, etc.).
* **Non-Interruptible:** This phase cannot be paused or delayed. If it were interrupted, the UI would render a fragmented, partially updated layout onto the screen.

## 📊 Summary Cheat Sheet

| Core Concept | Where it Operates | Primary Purpose | Interruptible? |
| --- | --- | --- | --- |
| **Virtual DOM** | Memory Heap | A lightweight blueprint of the layout used to bypass interacting directly with the real DOM. | N/A |
| **Rendering** | JavaScript Engine | Executing component functions to compute a fresh UI snapshot. | Yes (in concurrent mode) |
| **Reconciliation** | Diffing Engine | Comparing the new VDOM snapshot with the old snapshot to generate a patch list of changes. | Yes |
| **Fiber** | Core Architecture | The underlying scheduler that chunkifies tree updates into a linked-list framework to avoid blocking the main thread. | **Yes** (During Render phase) / **No** (During Commit phase) |
