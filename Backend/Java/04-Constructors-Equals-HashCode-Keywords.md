# Constructors, equals()/hashCode(), and the final/finally/finalize Trio

These are the mechanics every Java class actually relies on: how an object gets initialized, how it proves "I am equal to that other object" to a `HashMap`, and three same-sounding keywords that mean three completely different things.

## 1. Constructors, `this`, and Static Blocks

A constructor initializes a new object. It has no return type (not even `void`), and its name matches the class exactly.

```java
class Order {
    private final Long id;
    private final String customerEmail;

    Order(Long id) {          // parameterized constructor
        this(id, "unknown@example.com"); // this(...) delegates to another constructor — must be the first line
    }

    Order(Long id, String customerEmail) {
        this.id = id;                   // this.id disambiguates the field from the parameter
        this.customerEmail = customerEmail;
    }
}
```

- `this.field` distinguishes an instance field from a same-named parameter or local variable.
- `this(...)` calls another constructor in the same class and, like `super(...)`, must be the very first statement.
- A **default constructor** (no-arg, does nothing but call `super()`) is generated by Java only if you declare *no* constructor at all. The moment you write one constructor yourself, Java stops generating the default one.

```java
class FeatureFlags {
    static final Map<String, Boolean> flags;

    static {                             // static block — runs once, when the class is first loaded
        flags = new HashMap<>();
        flags.put("auditEnabled", loadFromConfig());
    }
}
```

A static block runs exactly once, when the class is loaded — before any constructor of that class runs, and before `main()` if that class is the entry point. It's the real-world tool for one-time static setup that's too complex for a simple field initializer, like the config load above. Order of execution for a new object: static block (once, class load) → instance field initializers → constructor body.

## 2. equals() and hashCode() — the Contract That Backs Every HashMap/HashSet

`Object.equals()` defaults to reference comparison (same as `==`); `Object.hashCode()` defaults to something derived from the object's identity. Neither is what you want for a domain object like `Order` that should be "equal" based on its data.

```java
class ProductSku {
    private final String code;

    ProductSku(String code) { this.code = code; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                 // fast path
        if (!(o instanceof ProductSku other)) return false;
        return code.equals(other.code);
    }

    @Override
    public int hashCode() {
        return Objects.hash(code);
    }
}
```

**Why both matter together:** a `HashSet`/`HashMap` first calls `hashCode()` to pick a bucket, then uses `equals()` to find the exact match *within* that bucket. If you override `equals()` but leave the default `hashCode()`, two logically equal objects can land in different buckets and the set will never recognize them as duplicates:

```java
Set<ProductSku> skus = new HashSet<>();
skus.add(new ProductSku("SKU-100"));
skus.add(new ProductSku("SKU-100"));
System.out.println(skus.size()); // 2, not 1 — if hashCode() wasn't overridden to match equals()
```

**The contract:** if `a.equals(b)` is `true`, then `a.hashCode()` **must** equal `b.hashCode()`. The reverse isn't required — two unequal objects are allowed to share a hash code (that's a **collision**, resolved by `equals()` inside the bucket, using a linked list or, since Java 8, a balanced tree once a bucket gets crowded enough).

A related real bug: **never mutate a field that's part of `equals()`/`hashCode()` after the object has been put into a `HashSet`/`HashMap` key** — its bucket location was computed from the old value, so lookups for it will silently fail afterward. This is the same underlying issue as the JPA entity `equals()`/`hashCode()` discussion in the [Database/JPA guide](../Backend/03-Database-JPA-Hibernate.md#36-equals-and-hashcode-on-entities), because JPA entities have exactly this same mutable-key problem.

## 3. final vs finally vs finalize

Three words that sound related and are not.

```java
final int MAX_RETRIES = 3;      // final: a keyword — restricts change

class ImmutablePoint {
    final int x, y;              // final field — must be set once (constructor or declaration), never again
}

final class ImmutablePoint2 { }  // final class — cannot be extended

class Base {
    final void validate() { }    // final method — cannot be overridden
}
```

```java
try {
    processPayment(order);
} catch (PaymentException e) {
    log.error("Payment failed", e);
} finally {
    releaseInventoryLock(order); // finally: a block — runs whether or not an exception occurred
}
```

`finally` is the correct place to release a resource that must always be released — a lock, a connection borrowed from a pool — regardless of success or failure. It is skipped only by `System.exit()` or a JVM crash; ordinary exceptions and even `return` statements inside `try`/`catch` still let `finally` run first.

```java
class TempFileHandle {
    @Override
    protected void finalize() { // finalize(): a method — called by the GC before reclaiming an object
        System.out.println("cleaning up");
    }
}
```

`finalize()` is **deprecated and unreliable** — the GC gives no guarantee about *when* (or even *whether*) it runs before the JVM exits, and relying on it for real cleanup (closing a file handle, a socket) is a production bug waiting to happen. The modern replacement is `try`-with-resources and `AutoCloseable` (see the [Exception Handling guide](07-Exception-Handling.md)), which run deterministically.

| | `final` | `finally` | `finalize()` |
|---|---|---|---|
| What it is | Keyword | Block | Method (deprecated) |
| Applies to | Variable, method, class | A `try` statement | Any object, called by GC |
| Guaranteed to run/apply? | N/A — enforced at compile time | Yes (except `System.exit`/crash) | No — unreliable, avoid |
| Modern replacement | — | — | `try`-with-resources / `AutoCloseable` |

## Interview Questions and Answers

### 1. Why must `this(...)` or `super(...)` be the first statement in a constructor?

**Answer:** Java requires the object's parent state (or an alternate constructor's initialization) to be fully set up before this constructor's own body runs, so there's a single, unambiguous initialization order. Allowing it anywhere else would let a constructor use fields before they're guaranteed to exist.

### 2. When does a static block run, relative to instance field initializers and the constructor?

**Answer:** Exactly once, the first time the class is loaded — before any instance of that class is created, and therefore before any field initializer or constructor body runs for that class.

### 3. Why does overriding `equals()` without `hashCode()` break a `HashSet`?

**Answer:** A `HashSet` uses `hashCode()` to choose a bucket first, then `equals()` to compare within that bucket. If `hashCode()` is left at its default (identity-based), two logically-equal objects can hash to different buckets and never get compared with `equals()` at all — so the set treats them as distinct even though your `equals()` says they're the same.

### 4. What's the exact contract between `equals()` and `hashCode()`?

**Answer:** If two objects are equal according to `equals()`, they must return the same `hashCode()`. The converse isn't required — two unequal objects can share a hash code, which is a collision, and `equals()` is what distinguishes them within the same bucket.

### 5. Why is mutating a field used in `equals()`/`hashCode()` dangerous after the object is stored as a map/set key?

**Answer:** The object's bucket was computed from the field's value at insertion time. Changing that field afterward doesn't move the object to a new bucket, so a later lookup with the updated (or original) value computes a different bucket than where the object actually lives, and the lookup silently fails to find it.

### 6. Difference between `final`, `finally`, and `finalize()`?

**Answer:** `final` is a keyword restricting reassignment, overriding, or extension. `finally` is a block that always runs after a `try` (barring `System.exit()` or a crash), typically for cleanup. `finalize()` is a deprecated, unreliable method the GC may call before reclaiming an object — real cleanup should use `try`-with-resources instead.

### 7. Can a `finally` block be skipped?

**Answer:** Yes, in two cases: `System.exit()` terminates the JVM immediately without running pending `finally` blocks, and a JVM crash obviously skips everything. Under normal exception flow — even a `return` inside `try` or `catch` — `finally` still runs first.

### 8. Why was `finalize()` effectively phased out in favor of `try`-with-resources?

**Answer:** `finalize()` gives no guarantee about when the GC will call it, or whether it runs at all before JVM shutdown — unpredictable timing that made resource cleanup (files, sockets, connections) unreliable. `try`-with-resources calls `close()` deterministically as soon as the block exits, success or failure.
